# Documentation Reviewer v0.1 — Design

## Цель

Создать локальный desktop-инструмент для проверки русскоязычного Markdown/Diplodoc-проекта. Первая версия выполняет только детерминированные проверки и показывает замечания; она не изменяет документацию и не отправляет данные в интернет.

## Область v0.1

- Платформа: Windows desktop.
- Источник: существующий локальный проект `diplodoc-example`.
- Область анализа: только `docs/ru`.
- `docs/en` и другие каталоги не участвуют в проверках.
- Формат документации: Markdown с конструкциями Diplodoc/YFM.
- AI/LLM отсутствует.
- Автоисправления отсутствуют.
- GitLab, сервер, учетные записи, база данных и история запусков отсутствуют.

## Технологии

- Electron — desktop-оболочка и доступ к локальной файловой системе.
- React — пользовательский интерфейс.
- TypeScript — приложение и движок проверок.
- Review Engine отделен от UI, чтобы позднее его можно было переиспользовать в CLI, VS Code extension или CI.

## Основной сценарий

1. Пользователь запускает приложение.
2. Выбирает корневую папку проекта.
3. Приложение определяет область документации `docs/ru`.
4. Пользователь нажимает **Проверить проект**.
5. Scanner получает список Markdown-файлов в `docs/ru`.
6. Parser извлекает ссылки, явные якоря и текстовые фрагменты, необходимые правилам.
7. Rules выполняют проверки.
8. Review Engine формирует единый список Findings.
9. UI показывает статистику и список замечаний.
10. При выборе замечания справа отображаются подробности.

## Первые проверки

### 1. Битая локальная ссылка

Проверяет ссылки на локальные Markdown-файлы. Если целевого файла нет в `docs/ru`, создается ошибка.

Severity: `error`.

### 2. Несуществующий якорь

Для локальной ссылки вида `file.md#anchor` проверяет наличие целевого файла и соответствующего якоря.

Severity: `error`.

### 3. Дублирующийся явный якорь

Проверяет явные идентификаторы Diplodoc/YFM вида `{#anchor}`. Повтор одного идентификатора в анализируемой области считается ошибкой.

Severity: `error`.

### 4. Пустая ссылка

Проверяет Markdown-ссылки с отсутствующим адресом, например `[Подробнее]()`.

Severity: `error`.

### 5. Нежелательная формулировка

Сверяет русский текст с локальным набором правил. Правило содержит нежелательную формулировку и рекомендуемый вариант. Ничего автоматически не заменяется.

Severity: `warning`.

### Изображения

Проверка физического наличия изображений не входит в v0.1. В рабочей документации изображения могут храниться в бакете и подключаться через preset, поэтому локальное отсутствие файла не является ошибкой. Проверка синтаксиса таких ссылок будет спроектирована позднее на реальном примере.

## Формат Finding

Каждое правило возвращает структурированное замечание:

- `ruleId` — идентификатор правила;
- `category` — категория;
- `severity` — `error`, `warning` или `info`;
- `file` — путь относительно `docs/ru`;
- `line` — номер строки;
- `title` — краткое название проблемы;
- `message` — объяснение;
- `source` — проблемный фрагмент;
- `recommendation` — что пользователь должен проверить;
- `target` — необязательная цель ссылки/якоря.

Правила не управляют отображением UI.

## Интерфейс

Используется двухпанельный вариант.

### Верхняя область

- выбранный проект;
- путь к `docs/ru`;
- кнопка **Выбрать**;
- кнопка **Проверить проект**;
- число проверенных файлов;
- общее число замечаний.

### Левая панель

Список замечаний. Для каждого элемента:

- severity;
- файл;
- строка;
- краткое название.

Фильтры:

- все;
- ошибки;
- предупреждения;
- по правилу;
- по файлу.

### Правая панель

Подробности выбранного Finding:

- название;
- severity;
- rule ID;
- файл и строка;
- описание проблемы;
- исходный фрагмент;
- рекомендация.

Кнопки автоисправления отсутствуют.

## Безопасность

- Документация читается только с локального диска.
- Приложение не отправляет содержимое документов наружу.
- Для v0.1 сетевые интеграции не нужны.
- Файлы документации открываются только для чтения.
- Review Engine не изменяет исходные файлы.

## Архитектурные компоненты

### Scanner

Получает корневой каталог `docs/ru` и возвращает набор анализируемых Markdown-файлов.

### Parser

Извлекает из Markdown минимальную структурированную информацию, необходимую правилам: ссылки, явные якоря, строки и текстовые фрагменты.

### Rules

Независимые проверки с единым интерфейсом. Каждое правило получает контекст проекта/документа и возвращает `Finding[]`.

### Reporter

Объединяет Findings, сортирует и передает результат UI.

### UI

Не знает внутренней логики правил и только отображает результаты Review Engine.

## Обработка ошибок

- Неверная выбранная папка: показать понятное сообщение, не запускать анализ.
- Нет `docs/ru`: сообщить, что область документации не найдена.
- Нет Markdown-файлов: завершить проверку без ошибки и показать нулевой результат.
- Файл невозможно прочитать: создать диагностическое сообщение приложения; остальные файлы продолжить проверять.
- Ошибка одного правила не должна останавливать остальные проверки.

## Тестирование

Для каждого правила создается отдельный минимальный fixture/тест.

Кроме unit-тестов выполняется контрольный интеграционный сценарий на копии существующего проекта:

1. Внести пять заранее известных проблем — по одной на каждое правило.
2. Запустить Review Engine.
3. Получить ровно пять ожидаемых Findings.
4. Проверить rule ID, severity, файл и строку каждого Finding.
5. Убедиться в отсутствии ложных срабатываний.

Рабочие пользовательские файлы не должны намеренно портиться тестами: тесты используют fixtures или временную копию.

## Критерий готовности v0.1

Пользователь выбирает `diplodoc-example`, запускает проверку и получает корректный отчет по `docs/ru`. На контрольном наборе из пяти известных проблем приложение находит ровно пять ожидаемых замечаний с правильными файлами и строками.

## Не входит в v0.1

- AI/LLM;
- проверка смысловых противоречий;
- проверка терминологии с помощью AI;
- проверка существования изображений в бакете;
- автоисправления;
- редактирование Markdown;
- GitLab/GitHub;
- CI;
- VS Code extension;
- история качества;
- Documentation Graph;
- база данных;
- авторизация и роли.
